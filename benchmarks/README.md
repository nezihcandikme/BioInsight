# Benchmarking DEConcord against DESeq2 and edgeR

DEConcord's own README has said this from the start: its differential
expression step is a simple, exploratory mean-difference t-test on
normalized log2 CPM values, not count-based negative-binomial modeling
like DESeq2 or edgeR. That's a design choice, not an oversight — but a
claim like that is only worth something if it's actually been checked
against the tools it's naming. This directory is that check.

## Datasets

**`airway`** (the original benchmark) —
[Bioconductor](https://bioconductor.org/packages/release/data/experiment/html/airway.html)
(Himes et al. 2014, *PLoS ONE*; GEO
[GSE52778](https://www.ncbi.nlm.nih.gov/geo/query/acc.cgi?acc=GSE52778)):
8 human airway smooth muscle RNA-seq samples, 4 cell lines, each with an
untreated and a dexamethasone-treated sample. It's the dataset DESeq2's
own vignette uses as its worked example — a standard, well-understood
choice, not one picked because it happens to flatter DEConcord.

**`pasilla`** (the second, independent benchmark) —
[Bioconductor](https://bioconductor.org/packages/release/data/experiment/html/pasilla.html)
(Brooks et al. 2011, *Genome Research*; GEO
[GSE18508](https://www.ncbi.nlm.nih.gov/geo/query/acc.cgi?acc=GSE18508)):
7 *Drosophila* S2-DRSC cell RNA-seq samples, RNAi knockdown of *pasilla*
(the fly homolog of human NOVA1/2) vs. untreated control. Different
organism, different design, different lab from `airway` — added
specifically to check whether the precision/recall numbers found on
`airway` are a property of the method or just a property of that one
dataset. It's the second dataset the DESeq2 vignette itself walks through,
for the same "standard, not cherry-picked" reason `airway` was chosen.

## Running it

Requires R with Bioconductor (`DESeq2`, `edgeR`, and the dataset package —
each script installs its own via `BiocManager` if missing) and this
repo's Python environment.

```
Rscript benchmarks/run_deseq2_edger.R
python benchmarks/compare_results.py
python benchmarks/compare_results.py --method moderated

Rscript benchmarks/run_deseq2_edger_pasilla.R
python benchmarks/compare_results.py --dataset pasilla
python benchmarks/compare_results.py --dataset pasilla --method moderated
```

Each R script writes its raw count matrix and sample metadata to
`benchmarks/data/`, runs DESeq2 and edgeR with each package's own
standard workflow (default settings, `filterByExpr` for edgeR, no
tuning toward any particular outcome), and writes their results to
`benchmarks/results/`. `compare_results.py` then runs DEConcord
(`run_analysis`, `min_count=10, min_samples=4`) on the exact same
count matrix and the exact same two groups, and reports:

- Pearson and Spearman correlation of log fold change, per gene, against
  each tool
- overlap of "significant" gene calls (DEConcord's default
  `adjusted_p_value < 0.05` and `|log_fold_change| > 1` vs. each tool's
  `padj`/`FDR < 0.05`) as a Jaccard index, precision, and recall
- a scatter plot of DEConcord's log fold change against each tool's,
  saved as `benchmarks/results/lfc_vs_deseq2.png` and `lfc_vs_edger.png`
  (or `..._pasilla.png` for the second dataset)

`--dataset` selects which benchmark dataset to run (`airway`, the
default, or `pasilla`); `--method` selects which of DEConcord's two DE
methods to benchmark: `welch` (default) or `moderated` (DEConcord's
empirical-Bayes variance-shrinkage option). Both dataset and method are
independent axes — `airway`/`pasilla` × `welch`/`moderated` all write to
distinct, non-overwriting filenames (`airway` + `welch` keeps the
original, unsuffixed names; every other combination gets a suffix, e.g.
`comparison_summary_pasilla_moderated.md`).

`benchmarks/data/` (the raw count matrices) and the full per-gene
`*deseq2_results.csv`/`*edger_results.csv` in `benchmarks/results/` are
gitignored and regenerated by running the scripts above. The small,
human-readable outputs — `comparison_summary*.md` and the scatter plots —
are committed, since they're the actual record of what was found.

## How to read the numbers, honestly

A few things worth knowing before treating any correlation or overlap
number here as a verdict:

**High log fold change correlation is expected and is the easy part.**
`compute_log_fold_change` is a plain difference of group means on log2
CPM — a simple plug-in estimate. DESeq2 and edgeR report a *shrunken*
effect size, pulled toward zero more aggressively for low-count, noisy
genes. The two should track each other well in direction and rough
magnitude (that's basic algebra, both are approximating the same
underlying ratio), but won't match exactly, and won't match least of
all for the lowest-count genes, which is exactly where shrinkage does
the most work.

**Significance-call overlap is the harder, more informative number, and
it isn't expected to be 1.0.** DEConcord tests per-gene variance with a
t-test on normalized values; DESeq2 and edgeR model the mean-variance
relationship across *all* genes at once and borrow statistical strength
across genes with similar expression levels. That's a real, substantive
methodological difference, not a bug in either approach — a gene with
noisy replicates will often look significant to a naive per-gene test
and not to a tool that's borrowed information from thousands of other
genes to get a better dispersion estimate. Disagreement here is data,
not failure.

**This doesn't "validate" DEConcord and isn't meant to.** It measures
the actual size of the gap between a simple exploratory method and the
field's standard tools, on the real datasets checked so far. If the gap
turns out to be small for genes with clear, large effects and large for
marginal ones, that's a specific, useful, falsifiable claim to make about
when DEConcord's numbers are trustworthy — a much stronger statement than
"it works on toy data," which is all that could honestly be said before
this existed. Two datasets is a real check, not a large one; the
[README](../README.md#limitations) says so directly.

Whatever the actual numbers come out to be, they get written up as-run
in `DEVLOG.md` — including if they're unflattering.

## Method concordance: DESeq2 vs edgeR

`compare_results.py` above answers "how close is DEConcord's simple
t-test to the field's standard tools" — a question about DEConcord.
`method_concordance.py` answers DEConcord's actual core question instead:
how much do DESeq2 and edgeR — two established, independently developed
tools — agree with *each other* on the same count matrix? It runs no DE
method itself; it just loads the same `*_deseq2_results.csv`/
`*_edger_results.csv` the R scripts above already produced and hands them
to `deconcord.concordance.methods.compute_de_concordance`, the same
library function anyone using DEConcord on their own two result tables
would call.

```
python benchmarks/method_concordance.py
python benchmarks/method_concordance.py --dataset pasilla
```

Writes `benchmarks/results/method_concordance.md` (`..._pasilla.md` for
the second dataset). On both datasets checked so far, DESeq2 and edgeR
agree strongly: Jaccard index ~0.76–0.78 on significant-gene overlap,
log fold change Pearson r > 0.998, and 100% directional agreement (zero
discordant genes) among genes both tools call significant — the
disagreement that exists is almost entirely about which *marginal* genes
clear each tool's own significance threshold (mostly genes DESeq2 calls
significant that edgeR doesn't), not about direction or magnitude for the
genes both agree are real. That's a real finding, not a given — it's
also exactly the kind of number this project exists to check across a lot
more conditions than just "DESeq2 vs edgeR, default settings, two
datasets."

## Stress test, regime 1: unbalanced groups

Every dataset checked above is a clean, balanced two-group design (4 vs
4, or close to it). Real studies aren't always that tidy — rare
conditions, limited biopsy material, and uneven attrition all produce
unbalanced group sizes routinely. This regime asks the same method
concordance question as above, but as one group's sample size shrinks
relative to the other's.

`run_stress_unbalanced.R` builds three real sample-subset levels from
Bottomly's 21 real samples (10 B6, 11 D2 — the most replication of any
dataset in hand), holding D2 fixed at its full 11 samples and shrinking
B6, so the imbalance ratio is isolated from "there's just less total
data": `balanced` (10 vs 11, the real full design), `moderate` (5 vs 11),
`severe` (2 vs 11, the practical floor — every tool here needs at least 2
replicates in a group to estimate any within-group variance at all). No
expression values are fabricated; every level is a real subset of real
samples, chosen deterministically (sorted sample ID, first N), never
cherry-picked. DESeq2, edgeR, and limma-voom each run their own
unmodified, default workflow at every level.

```
Rscript benchmarks/run_deseq2_edger_bottomly.R   # if benchmarks/data/bottomly_*.csv don't already exist
Rscript benchmarks/run_stress_unbalanced.R
python benchmarks/analyze_stress_unbalanced.py
```

Writes `benchmarks/results/stress_unbalanced_summary.md`, the same
pairwise `compute_de_concordance` numbers `method_concordance.py`
reports, at each of the three levels, plus a gradient table across
levels. `benchmarks/results/stress_unbalanced/` (per-level metadata and
each tool's full result table) is gitignored and regenerated by the
scripts above; the summary markdown is the committed record.

**Results, real run:**

| level (B6 vs D2) | pair | genes compared | Jaccard (sig. overlap) | log2FC Pearson r | directional agreement | discordant genes |
|---|---|---:|---:|---:|---:|---:|
| balanced (10 v 11) | DESeq2 vs edgeR | 21,662 | 0.930 | 0.9998 | 1.000 | 0 |
| balanced (10 v 11) | DESeq2 vs limma-voom | 21,662 | 0.880 | 0.9847 | 1.000 | 0 |
| balanced (10 v 11) | edgeR vs limma-voom | 21,662 | 0.921 | 0.9842 | 1.000 | 0 |
| moderate (5 v 11) | DESeq2 vs edgeR | 22,650 | 0.843 | 0.9992 | 1.000 | 0 |
| moderate (5 v 11) | DESeq2 vs limma-voom | 22,650 | 0.780 | 0.9714 | 1.000 | 0 |
| moderate (5 v 11) | edgeR vs limma-voom | 22,652 | 0.878 | 0.9677 | 1.000 | 0 |
| severe (2 v 11) | DESeq2 vs edgeR | 24,126 | 0.704 | 0.9981 | 1.000 | 0 |
| severe (2 v 11) | DESeq2 vs limma-voom | 24,126 | 0.602 | 0.9593 | 1.000 | 0 |
| severe (2 v 11) | edgeR vs limma-voom | 24,133 | 0.822 | 0.9513 | 1.000 | 0 |

Read honestly: significance-overlap agreement (Jaccard) degrades
substantially and monotonically as the smaller group shrinks, for every
pair — DESeq2 vs edgeR drops from 0.930 to 0.704, DESeq2 vs limma-voom
from 0.880 to 0.602 (the steepest decline of the three, and the weakest
pair at every level), edgeR vs limma-voom from 0.921 to 0.822 (the most
imbalance-robust pair). Log fold change correlation degrades too, but
much more gently for the DESeq2-edgeR pair specifically (0.9998 to
0.9981, barely moving) than for either pair involving limma-voom (both
drop roughly 0.02–0.03). What does **not** move, at all, at any level: 0
discordant genes and 100% directional agreement, every time, for every
pair, down to 2 samples in the smaller group. When these tools jointly
call a gene significant, they never disagree about the direction of the
effect, even as they disagree substantially more about *which* genes
clear that bar in the first place.

A plausible reading, not asserted as proven from one dataset: with fewer
replicates, each tool's own within-group variance estimate (DESeq2's
dispersion shrinkage, edgeR's, limma-voom's mean-variance trend in
`voom`) gets noisier and more tool-specific, which mostly affects the
threshold-crossing decision (is this gene's p-value on which side of
0.05) rather than the underlying effect size or its sign. Significance
calls get less reproducible across tools as groups shrink; the biological
direction of an effect, once detected, doesn't. This is one dataset, one
direction of imbalance construction (shrinking B6, not D2), and one
significance threshold (0.05) — a real finding on the data checked, not
a general law about these three tools under every kind of imbalance.

## Stress test, regime 2: batch effects

A batch effect needs a real confound to be a real test — inventing one
by scaling counts for an arbitrary sample subset would fabricate the
exact signal being tested for. `run_stress_batch.R` instead uses a real,
data-derived technical grouping already present in Bottomly's real
counts: per-sample library size (total real read count). Samples are
split into `low_depth`/`high_depth` batches by a median split on this
real value, no fabrication anywhere. The regime: does correctly
modeling this real technical covariate change cross-tool concordance,
relative to ignoring it? Two design formulas, same real counts and
groups, run through DESeq2, edgeR, and limma-voom each: `naive`
(`~condition`, ignoring the real batch structure) and `adjusted`
(`~depth_batch + condition`, modeling it). Whether the real batch split
happens to correlate with condition (B6 vs D2) is reported as-is, not
corrected for.

```
Rscript benchmarks/run_deseq2_edger_bottomly.R   # if benchmarks/data/bottomly_*.csv don't already exist
Rscript benchmarks/run_stress_batch.R
python benchmarks/analyze_stress_batch.py
```

Writes `benchmarks/results/stress_batch_summary.md`: the real batch x
condition contingency table, then pairwise `compute_de_concordance`
numbers for each tool pair under each of the two models, plus a
naive-vs-adjusted comparison table. `benchmarks/results/stress_batch/`
is gitignored and regenerated by the scripts above; the summary
markdown is the committed record.

**Results, real run:** the real median-split batch turned out only
mildly associated with condition, not a strong confound — `high_depth`:
4 B6 / 6 D2, `low_depth`: 6 B6 / 5 D2, close to independent.

| model | pair | genes compared | significant | Jaccard | log2FC Pearson r | directional agreement | discordant genes |
|---|---|---:|---:|---:|---:|---:|---:|
| naive (`~condition`) | DESeq2 vs edgeR | 21,662 | 3432 / 3264 | 0.930 | 0.9998 | 1.000 | 0 |
| naive | DESeq2 vs limma-voom | 21,662 | 3432 / 3136 | 0.880 | 0.9847 | 1.000 | 0 |
| naive | edgeR vs limma-voom | 21,662 | 3264 / 3136 | 0.921 | 0.9842 | 1.000 | 0 |
| adjusted (`~depth_batch + condition`) | DESeq2 vs edgeR | 21,662 | 3349 / 3162 | 0.916 | 0.9986 | 1.000 | 0 |
| adjusted | DESeq2 vs limma-voom | 21,662 | 3349 / 3015 | 0.875 | 0.9848 | 1.000 | 0 |
| adjusted | edgeR vs limma-voom | 21,662 | 3162 / 3015 | 0.922 | 0.9863 | 1.000 | 0 |

Read honestly: because the real batch split wasn't strongly confounded
with condition here, modeling it didn't dramatically change anything.
All three tools lose some power in the adjusted model (fewer genes called
significant across the board — DESeq2 3432 to 3349, edgeR 3264 to 3162,
limma-voom 3136 to 3015, the expected cost of spending a degree of
freedom on a real covariate), and Jaccard shifts by only about
0.005–0.015 per pair, in *both* directions (down for the DESeq2 pairs,
essentially flat to slightly up for edgeR vs limma-voom) — not the
one-directional degradation regime 1 showed. Directional agreement stays
exactly 1.000, zero discordant genes, in both models, same as every
other regime tested. The honest reading of this particular run: this
regime tested whether accounting for a *real but weak* technical
covariate changes concordance, and the answer on this data is barely,
in either direction — a stronger real confound (batch correlated more
tightly with condition) might show a bigger effect, and this result
doesn't rule that out, it just isn't what turned up here.

## Stress test, regime 3: low counts

`run_stress_lowcounts.R` reduces real sequencing depth by binomial
thinning: each real read in Bottomly's real count matrix is kept with a
fixed probability and dropped otherwise, the standard, well-established
way to simulate a shallower run from real data (the same logic behind
rarefaction and tools like `DropletUtils::downsampleMatrix`). It only
ever removes real reads, never invents a signal that wasn't there.
Three depths, same real 21 samples and groups throughout: `full` (the
real, unmodified data), `moderate` (25% of real depth), `low` (5%). A
fixed RNG seed (`set.seed(20260820)`) makes the thinning reproducible.
DESeq2, edgeR, and limma-voom each run their own unmodified default
workflow at every depth.

```
Rscript benchmarks/run_deseq2_edger_bottomly.R   # if benchmarks/data/bottomly_*.csv don't already exist
Rscript benchmarks/run_stress_lowcounts.R
python benchmarks/analyze_stress_lowcounts.py
```

Writes `benchmarks/results/stress_lowcounts_summary.md`: pairwise
`compute_de_concordance` numbers for each tool pair at each depth, plus
a gradient table across depths. `benchmarks/results/stress_lowcounts/`
(per-depth thinned counts and each tool's full result table) is
gitignored and regenerated by the scripts above; the summary markdown
is the committed record.

**Results, real run:**

| depth | total reads | pair | genes compared | Jaccard | log2FC Pearson r | directional agreement | discordant genes |
|---|---:|---|---:|---:|---:|---:|---:|
| full (100%) | 749,860,180 | DESeq2 vs edgeR | 21,662 | 0.930 | 0.9998 | 1.000 | 0 |
| full | 749,860,180 | DESeq2 vs limma-voom | 21,662 | 0.880 | 0.9847 | 1.000 | 0 |
| full | 749,860,180 | edgeR vs limma-voom | 21,662 | 0.921 | 0.9842 | 1.000 | 0 |
| moderate (25%) | 187,473,037 | DESeq2 vs edgeR | 17,585 | 0.908 | 0.9994 | 1.000 | 0 |
| moderate | 187,473,037 | DESeq2 vs limma-voom | 17,585 | 0.870 | 0.9910 | 1.000 | 0 |
| moderate | 187,473,037 | edgeR vs limma-voom | 17,585 | 0.924 | 0.9895 | 1.000 | 0 |
| low (5%) | 37,493,306 | DESeq2 vs edgeR | 12,933 | 0.890 | 0.9996 | 1.000 | 0 |
| low | 37,493,306 | DESeq2 vs limma-voom | 12,933 | 0.858 | 0.9910 | 1.000 | 0 |
| low | 37,493,306 | edgeR vs limma-voom | 12,933 | 0.908 | 0.9900 | 1.000 | 0 |

Read honestly, and it's a genuinely more forgiving pattern than
regime 1's: Jaccard degrades only mildly as depth drops 20-fold (full to
5%) — DESeq2 vs edgeR 0.930 to 0.890 (a 0.04 drop, versus a 0.226 drop
across regime 1's full imbalance sweep), DESeq2 vs limma-voom 0.880 to
0.858, edgeR vs limma-voom actually *ticks up* slightly at moderate
depth (0.921 to 0.924) before dropping to 0.908 at low depth, a small
enough wiggle to be noise rather than a real reversal. Log fold change
correlation doesn't consistently degrade at all — for the two pairs
involving limma-voom it's mildly *higher* at lower depth (DESeq2 vs
limma-voom: 0.9847 to 0.9910 to 0.9910; edgeR vs limma-voom: 0.9842 to
0.9895 to 0.9900), the opposite direction from regime 1. The likely
reason: independent/expression filtering gets more aggressive as depth
drops (21,662 genes tested at full depth, down to 17,585 at moderate,
12,933 at low), so the genes that still clear each tool's own
expression-filtering bar at low depth are disproportionately the
higher-count, more reliably estimated ones — the comparison is over
fewer genes, but a less noisy subset of them. Directional agreement:
exactly 1.000, zero discordant genes, at every depth, the same clean
result every regime in this suite has produced. One dataset, one
downsampling method (binomial thinning), one seed — a real finding on
the data checked, not a general law about depth robustness for these
three tools.

## Across all three regimes

The one number that never moved, in any of the ten level/model/depth
combinations tested across all three regimes (three imbalance levels,
two batch models, three depth levels — 24 tool-pair comparisons total):
**directional agreement among jointly-significant genes stayed at
exactly 1.000, zero discordant genes, every single time.** What moved,
and moved differently under each stress, was Jaccard (significance-set
overlap): substantially and monotonically under group imbalance (the
biggest effect of the three regimes), mildly and inconsistently under a
real-but-weak batch covariate, mildly under reduced sequencing depth.
Read together: for these three tools on this dataset, *which* genes
clear a significance threshold is the number sensitive to how clean the
data is; *whether two tools agree on a gene's direction once both have
called it significant* is not, at least not within the ranges of
imbalance, batch confounding, and depth reduction tested here. That's a
specific, falsifiable claim about where these three tools' agreement is
fragile and where it isn't, checked on real data, not asserted from
first principles.
